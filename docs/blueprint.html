Start here: the honest read

You picked custom distro, and that is the right call — but it's worth being precise about what it buys you, because the word "OS" hides two very different projects.

Writing a kernel from scratch means writing GPU drivers, a USB video stack, a network stack and an audio stack before your camera turns on. Nobody gets to Jarvis that way. What you actually want is the thing that feels like your OS: a machine where every package, service, kernel option and pixel of the desktop exists because you declared it, and where the interface is one you designed. That's completely achievable, and it's what this blueprint builds.

The constraint that shapes everything

This is your only PC and you still need Windows for gaming. So: a second physical SSD, not a shrunk partition. Windows keeps its own disk and its own bootloader, untouched. You pick the OS from the UEFI boot menu (F12 at POST on your Gigabyte board), never from a shared EFI partition that a Windows update can stomp on. Good news from your specs: you already own three drives, so this costs you nothing — see §07.

01

Choosing the base

Four ways to build a distro that's genuinely yours. Two of them are traps given your situation.

BaseWhat "from scratch" meansCost to youVerdict
NixOS
Pick this		 Nothing exists on the machine unless you declared it in code. The entire OS — kernel config, services, users, desktop, your Jarvis daemons — is one Git repo. The Nix language is genuinely strange for a week or two. Some binary blobs need nix-ld or a container to run. Atomic rollback. Every previous build stays in the boot menu, so a broken experiment is one reboot from fixed. On a single-PC project this is decisive.
Arch + custom kernel You install every package by hand and compile your own kernel. Very hands-on, very transparent. State drifts. Six months in, nobody — including you — knows why the machine is configured the way it is. Great teacher, poor foundation for a system an agent edits daily.
Gentoo Literally compile the whole userland from source with your own USE flags and -march=native. Days of compile time. Marginal real-world speedup. Satisfying, but you'd spend your first month watching GCC instead of building Jarvis.
Linux From Scratch Bootstrap the toolchain and every core package by hand, following the book. No package manager, no security updates, not reproducible. Trap Do it once in a VM as education. Never as your daily driver.

Why NixOS specifically, given that Claude Code is doing the building

An agent editing a mutable system leaves you with a machine whose current state is the sum of a thousand commands nobody logged. An agent editing a NixOS flake leaves you with a diff you can read. Every change is reviewable before it's applied, the build either succeeds or fails atomically, and if a change is bad you boot the previous generation. That property is the difference between "my agent is building my OS" and "my agent broke my only computer."

The layer stack

Seven layers, bottom to top. The ember ones are the parts you write; the rest you configure and compile.

L0 → L6 · build order is not bottom-to-top — see §09

L6
Jarvis HUD

The face. A Wayland layer-shell overlay: ambient status ring, live transcript, gesture-target highlight, gaze reticle, notification triage. Always on top, never stealing focus.

L5
Agent core — jv-brain, jv-act, jv-memory

Fuses perception into intent, decides, and acts. The only layer allowed to change the state of your machine.

L4
Perception services + message bus

Independent processes for hands, face, gaze, presence, speech and system context, all publishing to one local pub/sub bus. One crashing must never take down the others.

L3
Compositor — your Wayland shell

Windows, input routing, and the IPC surface Jarvis drives. Built on Smithay (Rust) or wlroots (C). Rent an existing one for the first six months.

L2
Userland

systemd units for every Jarvis service, PipeWire for audio, greetd for login, CUDA + cuDNN + TensorRT, ONNX Runtime, llama.cpp — all pinned in the flake.

L1
Kernel

Your own .config, seeded from make localmodconfig so it contains drivers for your hardware and nothing else. PREEMPT full and CONFIG_HZ=1000 for input latency; NVIDIA open modules; uvcvideo and uinput built in.

L0
Hardware

NVIDIA GPU, dedicated NVMe, IR webcam, hand-tracking sensor, far-field mic. See §07.

03

How Jarvis is wired

The single most important architectural decision: every sense is its own process, and they only ever talk through a bus. Not one big Python script. The reason is boring and non-negotiable — a segfault in the CUDA hand-tracking path must not silence your voice assistant, and you need to be able to restart, replace or rewrite any one sense without touching the rest.

The bus

A broker, jarvisd, listening on a Unix socket at /run/jarvis/bus.sock. Topic-based publish/subscribe, MessagePack frames, one schema directory that both Rust and Python generate their types from. Define those schemas before any service is written — see §10.

# frame envelope — every message on the bus
{
  "topic":  "vision.hands",        // dotted namespace
  "ts":     1755772800.041,        // capture time, monotonic
  "seq":    184203,
  "src":    "jv-hands",
  "conf":   0.94,                  // producers always state confidence
  "body":   { … topic-specific payload … }
}

04

The design problem nobody warns you about

Hand tracking is a solved problem. You will have working landmark detection in an afternoon. The thing that kills these projects is different, and it has a name.

The Midas touch problem

Once the camera watches your hands, everything you do with your hands becomes a command. You scratch your face and the volume drops. You reach for coffee and a window closes. Within two days you turn the feature off. Every gesture-control demo works; almost no gesture-control system survives contact with an actual work day.

Four mechanisms fix it, and you need all four:

  • 01An explicit engagement gate. Gestures do nothing until you arm them — an open palm held toward the sensor for 300 ms, or a hand entering a defined volume above the desk. Disarm on timeout. The gate must be visible in the HUD so you always know whether you're being read.
  • 02Gaze selects, hand confirms. This is why your two chosen features are worth more together than apart. Looking at a target is effortless and unambiguous; a pinch is a clean, deliberate confirm. Look at the window, pinch to focus. Look at the volume tile, pinch-and-drag. It is the interaction model Vision Pro shipped, and it is correct.
  • 03Design for a resting hand. Gorilla arm is real — a raised arm fatigues in under two minutes. Every gesture in your vocabulary should be performable with your forearm on the desk and your hand moving a few centimetres. This is also the strongest argument for a desk-mounted upward-facing sensor rather than a monitor-top webcam.
  • 04Hysteresis everywhere. Different thresholds to enter and leave a gesture state, plus a minimum dwell before firing. Without it, every classifier boundary flickers and your desktop twitches.

Calibrate your expectations for gaze

Webcam-based gaze estimation lands around 2–5° of visual angle. At 60 cm that's a 2–5 cm error circle — enough to know which window or monitor you're looking at, nowhere near enough to drive a cursor. Build zone-level attention features (auto-pause video when you look away, notify only in the region you're watching, dim the monitor you're ignoring) and treat cursor-grade gaze as a hardware upgrade, not a software problem.

05

The mind that remembers you

"It gets stronger every time I talk to it" is a memory-architecture problem, and it has a specific failure mode worth understanding before you write a line of it.

Why the obvious approach makes it worse over time

The default build is: embed every conversation, drop it in a vector database, retrieve the top-k similar chunks. This works beautifully for a month and then degrades — because as the store grows, retrieval returns more plausibly relevant and less actually relevant material, and the model drowns in it. Worse, it has no idea that something you said in March was superseded by something you said in August. It confidently tells you that you love a job you quit. A raw episodic pile doesn't compound; it accumulates.

What compounds is a system that distils. Five tiers, each with a different job and a different lifetime:

TierHoldsWritten byLifetime
WorkingThe current conversation and the last few hours of contextLive, in-contextHours
EpisodicAppend-only log of what happened: utterances, timestamps, active app, detected state. Ground truth, never edited.Every serviceForever (encrypted)
SemanticDistilled, typed facts about you — people, projects, preferences, routines, constraints, goals. This is the profile.jv-dreamUntil superseded or decayed
ProceduralLearned behaviour rules: don't talk before the first coffee, "fine" after 11pm means not fine. Each with an evidence count.jv-dream, promoted from patternsUntil contradicted
NarrativeDaily → weekly → monthly rollups. How you hold a five-year horizon in a finite context window.jv-dreamForever, compressing

The profile is a schema, not a blob

Every fact carries its own evidence. This is what lets you ask "why do you think that?" and get a real answer — and lets you correct it when it's wrong.

# one row in the semantic store
{
  "id":          "fact:person:maya",
  "kind":        "person",
  "value":       "Maya — sister, lives in Haifa, studying architecture",
  "confidence":  0.91,
  "first_seen":  "2026-09-03T21:14:02",
  "last_confirmed": "2026-11-27T08:41:55",
  "evidence":    ["ep:8841", "ep:9102", "ep:11733"],   // traceable to episodes
  "supersedes":  "fact:person:maya@v1",               // she moved; v1 said Tel Aviv
  "decay":       "slow"                              // people decay slower than moods
}

jv-dream — where the strengthening actually happens

A nightly job that runs when the machine is idle and you're not at it. It is the single most important service in the whole memory design, and it's the one everybody skips.

  1. Read today's episodes.
  2. Extract candidate facts, each with a proposed type and confidence.
  3. Reconcile against the existing profile — confirm (bump confidence, refresh last_confirmed), update, or mark superseded.
  4. Flag contradictions it can't resolve. These become questions for tomorrow, which is a far better reason to ask you something than a scripted prompt.
  5. Promote patterns seen enough times into procedural rules.
  6. Decay facts that haven't been reconfirmed. Forgetting is a feature — without it the profile fills with stale trivia and the signal drops.
  7. Write the day's narrative summary, and on Sundays fold the week into a weekly one.

This is the loop that makes it feel like it's growing. Talking to it adds episodes; jv-dream is what turns episodes into understanding.

First boot: the interview

The first conversation seeds the profile, so it's worth designing like a scene, not a settings wizard. Two constraints shape it: a wall of questions on day one is an interrogation, and generic questions get generic answers — "what are your hobbies?" produces a list jv-dream can do almost nothing with.

So: three questions on first boot, then two per day for the first week, each asked at a natural moment, each answerable only by you specifically. The questions that work share a trick — they ask for a relationship between things, not a list. Relationships are what the semantic store is made of.

Asks for a list

"What are your hobbies?"

"What music do you like?"

"Tell me about yourself."

Answerable on autopilot. Produces facts with no edges.

Asks for a relationship

"What's something you keep starting and abandoning — and what usually kills it?"

"Who in your life do you talk to less than you'd like?"

"What does a genuinely good day look like, hour by hour? Not a special day — a good ordinary one."

"When you're stressed, do you want to be handled with silence, distraction, or a plan?"

"What's a thing you're supposed to care about but don't?"

Each answer writes preferences, people, patterns and constraints in one pass — and question four calibrates its own behaviour toward you forever.

Three rules for the interview itself: every answer gets a follow-up drawn from the answer (that's what makes it a conversation and proves it listened); "skip" is always accepted without comment; and at the end of the week it plays back what it thinks it learned — "here's my picture of you so far, what did I get wrong?" — which both corrects the profile and teaches you that the profile is yours to edit. After that, scripted questions end forever; from then on, the only questions it asks are the ones jv-dream generates from real contradictions and gaps.

The greeting

Boot → jv-presence confirms it's you by IR face → jv-brain assembles time of day, time since last shutdown, calendar, and any open loops from yesterday's narrative. One or two sentences. Never a dashboard read aloud.

The rule that makes it feel real: the second sentence must be something only your assistant could say. If it would make sense on anyone's machine, cut it.

Generic

"Good morning! How can I help you today?"

"Good evening. You have 3 notifications."

Wallpaper by day three. You stop hearing it.

Earned

"Morning. You left the compositor branch half-merged — want me to open it?"

"It's 2am and that's the third night this week. The build will still be there tomorrow."

Requires memory. That's the whole point.

Use real signals rather than the clock alone: is this the first boot of the day or a reboot at 3pm? How long was the machine off — did you actually sleep? Is it a workday? Did yesterday end badly? A greeting derived from six signals feels alive; one derived from strftime feels like a screensaver.

Asking how you are — without it becoming a survey

You asked for this specifically, and it's the easiest thing in the whole project to get wrong. A scripted "how are you feeling?" becomes noise in about four days. Six rules keep it meaningful:

  • 01Never on entry. Nobody wants to be interviewed the second they sit down. Ask after a natural pause — a finished task, a closed window, a stretch of quiet.
  • 02Never while you're focused. jv-context and jv-face already know: gaze locked on the editor, fast typing, headphones on. Focus is sacred; the question waits.
  • 03Once a day, maximum. And skip days. Predictable check-ins get answered on autopilot, which makes the answers worthless.
  • 04Ask about something specific. "How did the thing with your landlord go?" beats "how are you feeling?" every time — it proves it was listening, and it's much harder to deflect with "fine".
  • 05Accept a non-answer. "Nothing" or silence ends it. No follow-up, no second attempt, no logging it as evasion. Pushing is how you teach yourself to resent it.
  • 06The answer must change its behaviour, not just fill a field. If you say you're wiped, it should go quiet, hold non-urgent notifications, and offer to move tomorrow's early meeting — visibly. An assistant that asks how you are and then behaves identically has learned nothing, and you'll know.

The proactivity budget

Silence is the default state. Give jv-brain a hard daily allowance of unprompted utterances — start at five — and make every category spend from it. When you dismiss or ignore something, that category's allowance shrinks; when you act on it, it grows. Within a couple of weeks the budget has been reallocated to whatever is actually useful to you, and it did that on its own.

This one constraint is the difference between an assistant and a nag, and it's five lines of code.

Personality is a file in the repo

Keep the system prompt, the voice, the wake word and the behavioural rules in personality/ under version control. Then "it's being too chatty this week" is a diff you can read and revert, not a mystery. Let jv-dream propose edits to it based on what it's learned; never let it apply them unreviewed. You should always be able to answer the question "why is it acting like this?" by reading a file.

Four things to build in now, not later

Encrypt the episodic log. It will become the most sensitive file you have ever owned — years of what you said, when, and how you seemed. LUKS on the partition isn't enough once you're logged in; encrypt the store itself with a key that isn't sitting next to it.

Make "forget that" real. A command that genuinely deletes from episodic and semantic and narrative, and shows you what it removed. If forgetting is fake, you'll start self-censoring around your own computer, and then the whole thing is worthless.

Don't let it flatter you. An assistant that learns from you and agrees with everything builds a feedback loop that gets more confident and less useful over time. Put "disagree with me when you have reason to, and say why" in the personality file, and check periodically that it still does.

Point it outward, not inward. It has genuine information nobody else has — that you haven't seen anyone in nine days, that you've been up past 2am all week. The right use of that is a nudge toward the people in your life, not becoming the one you talk to instead. And there's a hard line worth writing into the personality file from day one: if it ever picks up on something serious — sustained low mood, a bad stretch that isn't lifting — its job is to say so plainly and encourage you to talk to a real person, not to try to be your therapist. Build the thing that makes your life bigger.

06

The face: a sci-fi UI that stays out of your way

Sci-fi UI is a trap with a narrow exit. The trap is the movie version — spinning rings, scrolling hex, radar sweeps over nothing. It demos well for a week and then it's noise you pay 15% of a GPU for. The exit is one rule, enforced without exceptions:

Every moving pixel encodes a real signal

Films fill screens with decoration because their interfaces don't have to be used for eight hours. Yours does. The ambient ring pulses because the mic is hot. The glow on a window edge means gaze-selected, awaiting confirm. A particle drifts toward the tray because a download is actually moving. If an element would animate the same way with all sensors unplugged, it's set dressing — cut it. What makes an interface feel like the future isn't ornament; it's the eerie sense that the machine knows what's happening. You have the perception stack to actually deliver that.

Parallax you can't get anywhere else

Everyone's parallax follows the mouse. Yours can follow your head — jv-face already publishes head pose at 30 Hz. Offset each depth layer by a small multiple of head position and the desktop stops being wallpaper and becomes a window into a volume: shift in your chair and the near layers slide past the far ones. This is the same head-coupled rendering trick behind the famous Wii-remote "VR without glasses" demo, it costs almost nothing on a modern GPU, and it is the single most sci-fi thing you will ever show anyone — precisely because it uses a sensor no normal desktop has.

# depth model — five layers, one uniform each
L-4  scene      far   ×0.010   slow drift, time-of-day palette, your "world"
L-3  grid             ×0.025   faint structural field, brightens near activity
L-2  workspace        ×0.000   windows — LOCKED. Content never parallaxes.
L-1  glass      near  ×0.045   HUD panels, blur + tint, slight counter-shift
L-0  reticle          gaze    selection glow, gesture arm state, voice ring

rules: ease toward target over ~200ms (never raw pose) · full stop when
a window is fullscreen · off on battery · off with prefers-reduced-motion

The one inviolable line in that table: the layer you read and type in never moves. Parallax lives in the frame around your work, not in it — that's the difference between depth and seasickness.

Clean means earned emptiness

The default state of the screen is your work and nothing else. No taskbar, no persistent widgets, no icon grid. Chrome exists only while it's being used:

  • Summoned, not resident. The status layer appears on a palm-up gesture, a wake word, or a glance at a hot corner — and evaporates when your gaze returns to work. jv-face knows where you're looking; use it to make UI yield.
  • Notifications respect attention. Focused (fast typing, gaze locked)? They queue silently and the ring shifts hue one step — glanceable, ignorable. Idle? They surface. This is jv-presence doing UI's job.
  • One accent color, and it means "Jarvis". The cyan (or whatever you choose) appears only where the system is speaking to you: selection, listening state, confirmations. Scarcity is what makes it read as a voice rather than a theme.
  • Sound as UI. Three or four short, quiet, distinct cues — armed, confirmed, dismissed. Films get their atmosphere from sound design as much as graphics; desktops ignore this entirely.

The voice: engineered, not synthesized-sounding

Counter-intuitive but critical: you don't get a "voice from the future" by picking a robotic TTS — cheap robot voices read as old, not futuristic, and you'll be listening to this thing hundreds of times a day. The film trick is the opposite: start from an excellent, calm, natural voice and pass it through a signature effects chain. JARVIS in the films is just a great voice actor with subtle processing.

  • Base: Piper for instant responses, Kokoro when quality matters — pick one voice and never change it. Consistency is identity.
  • The chain (a PipeWire filter-chain node, so it applies system-wide to anything jv-voice says): a gentle high-pass at ~120 Hz → a barely-audible harmonic layer pitched an octave up, mixed at −20 dB (the "synthetic shimmer") → a short plate reverb, 0.2 s, so it sounds like it's speaking from the room's speakers, not a phone → a soft limiter. Subtle is the entire game: at the right levels people ask "what voice is that?", at the wrong levels it's a Dalek.
  • Sidechain everything else: when it speaks, music and app audio duck by a few dB and recover. That single touch — the room making space for it — does more "future" than any filter.
  • Keep the chain in personality/voice.toml with the rest of the identity, and A/B it with your own ears before you commit.

Performance is part of the aesthetic

Nothing reads "cheap sci-fi" faster than a stuttering hologram. Budget the whole ambient scene — parallax, grid, particles — at under 2 ms of GPU per frame and near-zero when nothing changed, so it never contends with jv-hands inference or a game. Damage-track everything; an idle desktop should render at 0 fps, not 60. And theme tokens live in personality/theme.toml next to the voice and wake word — the look is versioned like everything else about it.

Hardware

Your Lenovo 510 FHD is a better starting point than you probably realise: it's an IR model with Windows Hello facial recognition, which means a second infrared stream. On Linux that typically appears as an extra /dev/video* node — the same one the Howdy face-unlock project uses. Infrared gives you presence detection and face identity in a dark room, for free. Keep it, mount it on the monitor, and use it for face, gaze and presence.

What it can't do is hands. 1080p30, rolling shutter, no depth, and a downward-from-the-monitor angle that forces you to raise your arm. That's the one purchase worth making first.

The 6 GB playbook

Everything fits, but nothing fits simultaneously at full size — so the design is about scheduling, not sacrifice:

  • Daytime brain: an 8B-class model, Q4, ~4.7 GB resident via llama.cpp — smart enough for tool-calling and conversation, small enough to leave headroom.
  • Ears on CPU: distil-Whisper small streams comfortably on the i5, keeping the GPU for the brain and hands. Wake word and VAD are trivially CPU.
  • Vision is cheap: MediaPipe hands + face together need well under 1 GB. They coexist with the brain.
  • Night brain: when you sleep, jv-dream swaps the 8B out and runs a much larger model (a ~30B MoE runs at usable speed on 32 GB of RAM, CPU-only) for consolidation. Your assistant literally thinks deeper about your day while the machine idles — this is where the 32 GB pays for itself.
  • Gaming: when a game launches, jv-brain unloads from VRAM automatically and voice falls back to CPU-only mode. One systemd target handles it.

The one upgrade that changes the project

Nothing on your machine needs replacing — but if you ever spend money on this build beyond the sensors, spend it on a 16 GB GPU (used RTX 3090s and 16 GB 4060 Ti / 5060 Ti-class cards are the value picks in 2026). It moves the daytime brain from 8B to 24–32B, which is the difference between an assistant that follows instructions and one that feels sharp. Everything in this blueprint is designed so that upgrade is a one-line change in the flake.

08

Running Windows software

This is not a compromise or a bolt-on — done properly it's a system-level capability, and there's a specific technique that makes the difference between "I have Wine installed" and "my OS runs .exe files."

Three layers, in increasing cost. Roughly 90% of Windows software needs only the first.

Layer A — PE binaries as first-class executables

The trick most Wine setups skip: register the PE format with the kernel through binfmt_misc. Once you do, ./setup.exe works from any shell, scripts can call Windows binaries directly, and double-clicking an installer in a file manager does the obvious thing. The kernel hands the file to Wine the same way it hands a #! script to bash. NixOS exposes this declaratively:

# modules/windows-compat.nix
{ pkgs, ... }: {
  boot.binfmt.registrations.windows = {
    magicOrExtension = "MZ";          // every PE file starts with these two bytes
    interpreter      = "${pkgs.wineWowPackages.stagingFull}/bin/wine";
    fixBinary        = true;           // resolve interpreter at registration, not exec
    preserveArgvZero = false;
  };

  // so the file manager and xdg-open agree
  environment.systemPackages = with pkgs; [
    wineWowPackages.stagingFull  winetricks
    bottles       // per-app prefix management, GUI
    umu-launcher  // Proton outside of Steam
    lutris
  ];
}

Pair it with MIME associations for application/x-ms-dos-executable, application/x-msi and application/x-ms-shortcut so xdg-open routes them correctly. Wine's native Wayland driver has been on by default since 9.22 and matured through the 10.x and 11.x series, so most apps now render straight to your compositor with no XWayland detour.

Prefix hygiene is the whole game

The single biggest cause of "Wine is unreliable" is one shared ~/.wine. A bad DLL override, a half-installed .NET runtime or a corrupt registry key then poisons every application at once. One prefix per app, always. Treat prefixes as cattle, not pets: if one misbehaves, delete it and rebuild from its recipe.

Layer B — Seamless Windows VM

For the software Wine will never handle: Office with full fidelity, the Adobe suite, anything with hardware DRM or a vendor driver stack. WinApps (and the newer WinBoat) run a Windows VM under libvirt or Podman and expose individual applications over FreeRDP RemoteApp — so Excel appears as a normal window on your desktop, with its own taskbar entry and file associations, not as a Windows desktop in a box.

Cost: a Windows licence, ~40 GB of disk, and 4–8 GB of RAM while it's running. Worth it if two or three apps are blocking you; not worth it as a default.

Layer C — VFIO GPU passthrough

Full GPU handed to a Windows VM. Real value only if you need native graphics performance inside Windows without rebooting. It wants a second GPU (single-GPU passthrough scripts exist but are fragile), cooperative IOMMU groups, and a weekend of your life. And since anti-cheat generally detects VMs anyway, gaming isn't the use case — that's what your dual boot is for. Skip unless proven necessary

What genuinely won't work

You asked for all games and software, so here is the honest boundary: the three layers above cover the overwhelming majority, and the dual boot covers the rest — but nothing makes kernel-anti-cheat titles run on Linux, and anyone who claims otherwise is selling something. The design goal is that rebooting into Windows becomes rare enough to feel like visiting, not living there.

  • Kernel-level anti-cheat. Vanguard, Faceit AC and similar require a real Windows kernel driver. Not Wine, not a VM. Dual boot.
  • EasyAntiCheat and BattlEye both can run under Proton — but only if the game's developer flipped the Linux switch. Many have; check ProtonDB per title before you assume.
  • Vendor driver stacks — printer/scanner suites, USB dongles, capture cards, anything installing a .sys.
  • Some DRM-wrapped installers that check for kernel signatures at install time.

The part that makes it JarvisOS: jv-compat

Everything above is a stock Linux setup. The interesting version is handing the whole lifecycle to Jarvis. You drop an installer in a folder, or just say "install this", and jv-compat:

  • fingerprints the binary — architecture, .NET or VC++ dependency, installer framework (NSIS, Inno Setup, MSI, WiX, Squirrel);
  • looks up a recipe in a local database, or synthesises one from the fingerprint;
  • creates a dedicated prefix and runs the installer silently where the framework supports it — /S for NSIS, /VERYSILENT for Inno, msiexec /qn for MSI;
  • harvests the resulting shortcut, extracts the icon, writes a proper .desktop entry and registers the file types it claims;
  • commits the recipe to your flake, so that app is reproducible on a fresh install.

The end state: Windows software installs on your machine the way an app installs on a phone. You never see a prefix, never open winecfg, never Google a DLL override.

Wine is not a sandbox

Worth being blunt: an .exe running under Wine executes as your user, with full read/write access to your home directory. Every advantage of "the OS runs Windows binaries transparently" is also an attack surface. Confine each prefix — bubblewrap or a Flatpak-style sandbox, with only the directories that app actually needs bind-mounted in, and no network unless it needs one. Build this into jv-compat from day one rather than retrofitting it, and make untrusted-binary confinement the default rather than the opt-in.

Jarvis as guardian: jv-guard

Since the OS runs Windows binaries transparently, the OS must also distrust them by default — so protection becomes a service with the same standing as hands or voice:

  • Every incoming binary is screened before it can run. Downloads and installers get hashed, checked against local ClamAV signatures and a VirusTotal hash lookup (hash only — the file never leaves your machine), and fingerprinted for known packer/dropper patterns. jv-compat refuses to build a prefix for anything that fails.
  • Detonation before trust. Unknown installers run first in a throwaway, network-blocked prefix while jv-guard watches what they touch. An installer that tries to write outside its prefix, register autostarts, or phone home gets reported to you in plain language — "this claims to be a PDF tool but it tried to reach three servers in the first ten seconds" — before anything permanent happens.
  • The sandbox rules above are enforcement, not advice: no Windows app sees your home directory, camera, mic, or network unless its recipe grants it. Jarvis can tell you exactly what any app has ever been allowed to touch, because it wrote the grants.
  • The Linux side is watched too: new systemd units, changed boot entries, unexpected listeners on the network — anything that diverges from what the flake declares is by definition suspect, which is a detection power normal antivirus can only dream of. The flake is the whitelist.

Worth saying plainly: this makes the machine far safer than a stock Windows box for running strange software — but no guard is absolute, and jv-guard will say "I'm not sure about this one" rather than pretend certainty. That honesty is part of the personality file.

Ground

It speaks

It acts

jv-act and the tool registry. Capability gating from the start: every tool declares its blast radius, and destructive ones require confirmation.

Stand up jv-compat here too — the binfmt registration and per-app prefixes are a day of work, and having .exe files just run removes the main reason you'd otherwise reboot into Windows.

Weeks 6–9

Hands

jv-hands plus the engagement gate, hysteresis, and a deliberately tiny vocabulary — six gestures, no more. Synthetic input through uinput. Build the replay harness here (§10): record sensor sessions to disk so you can iterate on the classifier without sitting in front of the camera.

✓ Palm up, pinch, scrub. Volume and window switching without touching the keyboard.
4
Weeks 9–12

Eyes and presence

jv-face and jv-presence. Auto-lock when you leave and IR face-unlock when you return. Attention-aware notifications. Auto-pause on look-away. Then the payoff: gaze-select fused with pinch-confirm in jv-act.

✓ You look at a window and pinch, and it focuses. The machine knows when you're there. It greets you by name when you sit down — see §05.
5
Months 4–6

Your shell

Now — and only now — write the compositor. Smithay if you want Rust and a modern codebase; wlroots if you'd rather stand on Sway's decade of hardening. Because you've been running against a rented compositor's IPC, you already know exactly which surface you need. Fold the HUD in as a native layer rather than an overlay client.

✓ Boot splash to desktop, every pixel yours. This is when it becomes JarvisOS.
6
Ongoing

Ambient

jv-memory and jv-dream earn their keep: routines learned rather than configured, workspace state restored by time of day and task, proactive suggestions that stay quiet when you're focused. Smart-home tools in the registry. This phase never really ends, which is the point.

Why the compositor is Phase 5 and not Phase 0

It's the most seductive part and the most common place these projects die. A compositor is months of work before it can display a single usable window, and every one of those months is a month without Jarvis. Rent one, learn what you need from using it, then write the one you actually want.

Rules for driving Claude Code on this

You said you'd have Claude Code build it. That works well here, but only if you impose structure on it. These are the rules that make the difference.

  • 01Contracts before code. Write every bus schema in schemas/ and freeze them before a single service exists. Then each service is an independent, testable task with a defined input and output — which is exactly the shape an agent builds well. Skip this and you get ten services that each invented their own message format.
  • 02One service, one session. Don't ask for "the perception layer." Ask for jv-hands, with its schema, its systemd unit, and its tests. Small bounded tasks with a clear definition of done.
  • 03Build the replay harness in Phase 3, not Phase 5. Recorded sensor sessions are the single highest-leverage thing in this repo. They let an agent iterate on gesture classification without a human sitting in front of a camera, and they turn "does this feel right?" into a test that runs in CI.
  • 04A CLAUDE.md that states the invariants. Processes never share memory. Only jv-act touches system state. Every producer publishes a confidence value. Nothing blocks the bus. Latency budgets are limits, not goals. Write these down or they will erode.
  • 05Never let it apply an untested boot or kernel change. nixos-rebuild build and read the diff; nixos-rebuild test to try it without touching the bootloader; switch only when it works. Your generation history is the safety net — don't let anything garbage-collect it while you're experimenting.
  • 06Review jv-act by hand, always. Everything else can crash harmlessly. This one has your keyboard, your filesystem and your shell. Read every tool it gains.
12

Risks worth pricing in now

The last 10% of Windows software

Layers A and B in §08 cover most of it, but kernel-level anti-cheat and vendor driver stacks never will. Before you commit, list the Windows software you actually can't live without and check each one on WineHQ AppDB and ProtonDB. That list decides how often you're really rebooting.

NVIDIA on Wayland

Vastly better than it was — open modules and explicit sync landed — but it's still the sharpest edge in this build, and it's the layer you can least afford to debug. Pin your driver version in the flake and change it deliberately.

Always-on camera and microphone

You're building a machine that watches and listens to you continuously. Keep every model local, log what's captured, and wire a real hardware kill switch — a USB power toggle you can hit without thinking. Also: the HUD must always show whether sensors are live.

Scope, honestly

Phases 0–4 are a solid full-time quarter and give you a Jarvis you use daily. Phase 5 is a second quarter on its own. Treat anything beyond that as bonus, and resist the urge to start the compositor early.
